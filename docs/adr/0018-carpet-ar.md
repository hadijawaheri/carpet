# 0018 · "See it in my room" through the phone's own AR viewer

Date: 2026-10-29 · Status: accepted (task C7: owner asked to see a carpet at its real size on the visitor's floor)

- **No AR code runs in the site.** The carpet page links to the viewer the phone already has: Quick Look on iPhone and iPad (`<a rel="ar">` to a USDZ), Scene Viewer on Android (an `intent://` link to a glTF, falling back to the carpet page). The site asks for no camera permission and ships no WebXR library; the CSP and `Permissions-Policy: camera=()` stay as they are. A computer shows a QR code to the carpet page instead, drawn on the server like the certificate's (docs/adr/0015).
- **The model is one flat rectangle at the catalogue size with the owner's photo on it**, in metres, lying on the floor. Nothing is modelled or drawn (CLAUDE.md: carpet images come only from the owner's photos). Both viewers open at a fixed scale (`resizable=false`, `allowsContentScaling=0`), because the point is to see the real size; a placeholder carpet says its size is not final.
- **Both files are written by hand** (`features/carpet-ar/model`): a GLB with one quad, and a USDZ that is an uncompressed zip with the USD text first and every file aligned to 64 bytes, as Apple requires. Each is a few dozen lines; three.js's exporters need a browser canvas, and a converter would be a native build dependency.
- **Served by route handlers** at `/carpets/[slug]/model.glb` and `model.usdz`. The texture is the carpet's photo re-encoded as JPEG at most 2048 px with `sharp`. Each URL carries `?v=` from a hash of photo and size: the current version is cached for a year (`immutable`), and any other `v` is a no-store 307 to the current one, so a new photo reaches phones at once. The photo is fetched from `NEXT_PUBLIC_SITE_URL` or, for uploads, straight from `INTERNAL_API_URL`, never from the request's Host, so a forged Host header cannot poison the cached model.
- Not verified on a real device from here: the files are checked structurally in unit and e2e tests (GLB header, chunk alignment, bounds; zip CRC, alignment, entry order). A first check on an iPhone and an Android phone with ARCore is still needed.
